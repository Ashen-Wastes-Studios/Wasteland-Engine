# Visual Blocks Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** A node-graph visual scripting system ("Visual Blocks") that lets a
designer wire gameplay logic in the DemonCore editor, compiles to Python, and
runs on an entity through the existing `ScriptEngine` — the same authoring
experience as UE5 Blueprints, at a fraction of the cost.

**Architecture:** Graphs are authored as `.wlblocks` (YAML) files. A C++
compiler validates the graph against a node registry and **transpiles it to
Python source**, which is written to disk and picked up by the existing
`ScriptComponent` / `ScriptEngine` path. No new runtime, no new VM, no new
binding layer. The editor gets an ImGui node-graph panel on top of
`imgui-node-editor`.

**Tech Stack:** C++17, yaml-cpp (already vendored), ImGui 1.89.3,
imgui-node-editor (to vendor), pybind11 + Python 3.14 (existing runtime),
entt ECS (existing).

---

## The one architectural decision that matters

**Visual Blocks compiles to Python. It does not implement a bytecode VM.**

This is the decision everything else follows from, so it goes first.

UE5 Blueprints compile to a custom VM with its own reflection system covering
the entire engine. Building that here means re-implementing a binding layer
for every node — and the engine *already has one*: `Bindings.cpp` is 3816
lines exposing Scene, entt components, Box3D physics, Raycast, MoveCapsule,
inventory, audio, animation, input, and math to Python. A VM would duplicate
all of it, in a second language, forever.

Compiling to Python instead gets:

| Concern | VM approach | Codegen approach |
|---|---|---|
| Every engine API as a node | Re-bind everything, twice | Already bound — wrap it |
| Debugging a broken graph | Custom debugger, new tooling | Read the generated `.py` in the existing ScriptEditorPanel |
| Error messages | New format | Real Python tracebacks with line numbers |
| Hot reload | New mechanism | `importlib.reload` (already in `ScriptEngine.cpp:99`) |
| Shipping to users | New binary format | A text file they can diff and hand-edit |
| Perf headroom | Best | Python overhead — acceptable, see Risks |
| Cost to build | Weeks | Days for the compiler, which is the hard part |

Blender's material/shader node graphs transpile to Python for exactly this
reason, and it is the established pattern for engines that already script in
Python. The proof obligation shifts from "does the VM work" to "does the
generated code run correctly", which is testable headlessly.

**The generated `.py` is a first-class artifact, not a throwaway.** It gets
pretty-printed, a header explaining it is generated and from what, and it is
openable in the existing script editor. If codegen produces something
embarrassing, the designer can read it and file a bug.

**Free wins this buys:**

- Custom events already work. `Interactor.py:102` calls
  `CallScriptMethod("OnInteract", ...)`, which does a `getattr` on the live

- Script hot-reload already works.
- The content browser already dispatches on extension — one line to open
  `.wlblocks` instead of `.py`.
- Generated code can call back into hand-written Python scripts, and vice
  versa. Mixed projects work from day one.

## File format: `.wlblocks`

YAML, because `.wastescene` and `project.wasteland` already are and
yaml-cpp is already a dependency.

```yaml
schema: 1
name: EnemyChase

# Instance variables -> generated as self.<name>, initialized in __init__
variables:
  - { name: target,    type: Entity, default: null }
  - { name: speed,     type: float,  default: 3.0 }
  - { name: attackTimer, type: float, default: 0.0 }

nodes:
  - { id: n1, type: EventOnUpdate, x: 0,   y: 0  }
  - { id: n2, type: Branch,         x: 260, y: 0  }
  - { id: n3, type: GetHealth,      x: 100, y: 120 }
  - { id: n4, type: SetVariable,    x: 420, y: 40 }

# Literal values for input pins with no link
pins:
  - { node: n4, pin: Value, value: 0.0 }

links:
  - { from: { node: n1, pin: Out },   to: { node: n2, pin: In } }
  - { from: { node: n3, pin: Health }, to: { node: n2, pin: Condition } }
```

**Pins are identified by stable string IDs, never indices.** A node definition
gaining a pin must not break every saved graph that used the old layout. This
is the single most important format decision and the easiest to get wrong.

The `Out` pin on event nodes and the `In` on flow nodes are the **exec** wire
type, distinct from data pins. UE5 draws them white and unconnected; so do we.

## Type system

Nine data types plus exec. Deliberately small — every added type is a
conversion rule to maintain across every node.

| Type | Python | Notes |
|---|---|---|
| `exec` | *(none)* | Control flow, not a value. Order matters. |
| `bool` | `bool` | |
| `int` | `int` | |
| `float` | `float` | `int` promotes implicitly to `float` on connect |
| `string` | `str` | |
| `vec2` | `Wasteland.Vec2` | |
| `vec3` | `Wasteland.Vec3` | |
| `vec4` | `Wasteland.Vec4` | |
| `entity` | `Wasteland.Entity` | Reference, not a copy |

Rules:
- A link is legal if the types are equal, or the source is `int` and the
  target is `float` (implicit promotion). Nothing else.
- Exec wires connect only to exec pins. Data wires never connect to exec.
- Every input pin is either linked or has a literal. A required pin with
  neither is a **compile error naming the node and pin**, not a silent default.

## Node registry

One table maps node type → pins + emitter. This is the extension point: a new
node is one registration, and it is available to the editor, the validator,
the codegen, and the docs from that single entry.

```cpp
// VisualBlocks/NodeRegistry.h
namespace Wasteland::VisualBlocks {

enum class PinType { Exec, Bool, Int, Float, String, Vec2, Vec3, Vec4, Entity };

enum class PinDir { In, Out };

struct PinDef {
    std::string Id;          // stable, persisted in .wlblocks
    std::string Label;       // shown to the designer
    PinType Type;
    PinDir Dir;
    bool Required = false;
    // Literal for an unconnected input pin. Stored as text; parsed per-type
    // at compile time so a malformed literal is a reported error, not a crash.
    std::string DefaultLiteral;
};

struct NodeDef {
    std::string TypeId;      // "SetVariable", persisted in .wlblocks
    std::string Category;    // "Variables", "Flow Control", "Scene", "Math"
    std::vector<PinDef> Pins;

    // Emits the node's Python. `in` is the expression string for each input
    // pin, keyed by PinDef::Id; `out` receives each output pin's expression.
    // Return an error string, empty on success.
    using EmitFn = std::function<std::string(const EmitContext &)>;
    EmitFn Emit;
};

class NodeRegistry {
public:
    static NodeRegistry &Get();
    const NodeDef *Find(const std::string &typeId) const;
    const std::vector<NodeDef> &All() const { return m_Defs; }
    void Register(NodeDef def);
private:
    std::vector<NodeDef> m_Defs;
};

}
```

`EmitContext` carries the node's id, the resolved input expressions, the
declaration list for temporaries, and the indent level. Node authors never
touch the generated file directly — they return an expression or a statement
block, and the emitter handles scoping and indentation.

## Code generation

Straightforward structured codegen, one Python function per event. Control
flow maps to native Python constructs rather than a jump table:

| Node | Emits |
|---|---|
| `Sequence` | statements in pin order |
| `Branch` | `if cond:` / `else:` |
| `Switch` | `if/elif/else` on the selector |
| `While` | `while cond:` |
| `ForEach` | `for item in coll:` |
| `Delay` | `yield` (see below) |

**Delays and latent actions.** `Delay` inside a per-frame `OnUpdateEntity` has
no meaning in a straight-line function. The fix is that each event graph
compiles to a Python **generator**, and the generated class drives it one step
per frame:

```python
class EnemyChase:
    def __init__(self, entity):
        self.entity = entity
        self.target = None
        self.speed = 3.0
        self.attackTimer = 0.0
        self._gen = None

    def OnUpdateEntity(self, dt):
        seconds = dt.GetSeconds()
        if seconds <= 0.0:
            return
        self._gen = self._ev_on_update(seconds)
        try:
            next(self._gen)
        except StopIteration:
            self._gen = None

    def _ev_on_update(self, __dt):
        __t1 = self.entity.TryGetHealthComponent()
        if __t1 is None:
            return
        if __t1.IsDead:
            return
        self.attackTimer = max(0.0, self.attackTimer - __dt)
        yield from __wl.delay(1.0)      # a Delay node
        self.entity.CallScriptMethod("OnOpen", self.entity)
```

`__wl.delay(seconds)` is a tiny generated-module helper that yields a deadline
and completes once `__dt` has accumulated past it. Suspending a graph halfway
through is exactly what UE5 latent actions do, and Python generators give it
to us without a scheduler. This is the clearest place codegen beats a
hand-rolled VM.

**Variable scoping.** A temp assigned inside a `While` or `ForEach` body
escapes the loop with its last value, same as UE5. Generated names are
Python-unique per node (`__t<n>`), so no collision. This is a documented
behavior, not a bug to be fixed later.

**Output shape.** Pretty-printed, never minified, with a header:

```python
# GENERATED BY VISUAL BLOCKS — DO NOT EDIT
# Source: assets/blocks/EnemyChase.wlblocks
# Graph schema 1, engine 0.1.0
# Edits here are lost on the next compile. Edit the graph, or copy this
# into a hand-written script and call it from a CallPythonMethod node.
```

  details panel for the selected node, compile-error list pinned to nodes.
- Vendored `imgui-node-editor` (thedmd) — MIT, ImGui 1.72+, has explicit fixes

## Phasing

Each phase ships independently and is headlessly verifiable. **No editor UI
is written until the compiler is proven correct** — the compiler is the hard
part and the UI is the easy part, and building the UI first means debugging two
new things at once.

```
VB.0 vendor node editor     ─┐
VB.1 data model + YAML       │ compile, no UI
VB.2 registry + types        │ all headless-testable
VB.3 codegen                 │
VB.4 end-to-end on an entity ┘
VB.5 editor panel  ── needs the compiler to already work
VB.6 debug/trace + AI authoring
```

### VB.0 — Vendor imgui-node-editor

`Wasteland/vendor/imgui-node-editor/` (header + sources), added to
`premake5.lua` alongside the existing ImGuizmo block, with the same
`filter "files:vendor/**.cpp" flags { "NoPCH" }` treatment. Verify it compiles
in both Debug and Release before writing a single line against it.

### VB.1 — Data model and serialization

`VisualBlocks/Graph.h/.cpp` — `Graph`, `GraphNode`, `GraphLink`, `PinLiteral`,
`GraphVariable`, `PinType`. `VisualBlocks/GraphSerializer.h/.cpp` — load/save
YAML via yaml-cpp, with an unknown-key and unknown-pin-type check that
**errors rather than silently dropping data**. A graph that loses a node on
save is worse than one that refuses to load.

Test: round-trip a graph with every field populated; the re-read file is
byte-identical. Load a graph with an unknown node type → error naming the
type and file, no partial load.

### VB.2 — Registry, type checking, validator

`VisualBlocks/NodeRegistry.h/.cpp` and `VisualBlocks/Validator.h/.cpp`.

Validator rejects, each with the offending node named:
- a link between incompatible types (except `int`→`float`)
- an exec wire into a data pin, or the reverse
- a cycle in the flow graph
- a required input pin with neither a link nor a literal
- a dangling link to a deleted node

Test: one case per rule, each asserting the error message names the node.

### VB.3 — Code generator

`VisualBlocks/Compiler.h/.cpp` — the transpiler. Emits one generator function
per event plus the `__init__` that initializes declared variables.

Test, all comparing emitted text against an expected string:
- linear graph of three nodes emits statements in pin order
- `Branch` emits a correct `if`/`else` and routes *both* successors
- `While` emits a `while` and the body's temps survive past the loop
- `Delay` emits `yield from __wl.delay(...)`
- two events emit two functions, both reachable from the dispatcher
- an unused output pin emits an assignment that is not dead code
- an `int` literal feeding a `float` pin emits `3.0`, not `3`
- re-compiling the same graph twice emits **byte-identical** output
  (determinism — a non-deterministic emitter makes every diff and every test
  a lie)

### VB.4 — End-to-end, headless

The proof. Compile a graph, write the `.py`, attach a `ScriptComponent`, run
`OnUpdateRuntime`, assert on read-back values.

Two graphs, in order:
1. **Rotator** — a straight-line `OnUpdate` that adds to rotation. If this does
   not pass, nothing else matters.
2. **EnemyChase** — a faithful rebuild of `Enemy.py` (200 lines: retarget on
   a timer, move toward target, smooth yaw, ground probe, contact damage on
   an interval). This is the real test: if a hand-written 200-line gameplay
   script can be expressed as a graph, the system is genuinely useful. If it
   cannot, the node library is missing something and that is worth learning
   now rather than after the editor exists.

Test asserts actual component values after N ticks — entity moved, rotation
changed, health dropped, timer reset. Not "did not throw".

### VB.5 — Editor panel

`DemonCore-Editor/src/Panels/VisualBlocksPanel.{h,cpp}`, wired into
`EditorLayer` next to the existing panels. Palette, canvas, details, error
list. Content browser extension dispatch.

Verify visually, with screenshots at 4K: place a node, drag a wire, hit
compile, see the generated Python, run it, see the entity move. A clean build
proves nothing here — the user is right to demand rendered proof.

### VB.6 — Trace, and AI authoring

- A trace toggle that logs each node as it executes, with the graph open in
  the editor. This is how you debug a visual language.
- The `ToolServer` already does `write_file` / `edit_file` against
  project-relative paths. A graph is a text file. The agentic `AIChatPanel`
  can author `.wlblocks` directly, and the existing validator becomes the
  error-checking pass. This is a genuine differentiator and it is nearly free
  once `.wlblocks` is a documented text format.

## Risks

**Loop/branch codegen is the hard part.** The compiler is ~80% of the
difficulty and everything else is UI. Mitigation: build and test it first,
headlessly, before any editor code exists (VB.1–VB.4 are all UI-free by
design).

**Python performance.** A graph-compiled enemy does strictly more work than a
hand-written one. For the entity counts this project targets (an arena
blockout, tens of entities) it is irrelevant. If it ever matters, the escape
hatch already exists: `CallPythonMethod` nodes, and hand-written Python
scripts called from graphs. Do not build a VM to solve a problem this codebase
does not have.

**`imgui-node-editor` is a third-party dependency** and its newest release
line targets ImGui 1.89+. Mitigation: vendor and compile it *first* (VB.0), so
a version incompatibility surfaces in the first hour rather than after the
compiler is done.

**Scope creep toward UE5.** The honest gap: no inheritance, no interfaces, no
subgraph-as-function until VB.6, no per-node breakpoints, no node comments.
Naming those as out of scope now is cheaper than discovering them in month
three. UE5 took a team years; matching its *authoring experience* for
single-entity gameplay logic is achievable in days, and that is the actual
goal.

**`ScriptComponent` currently stores a path, not a graph reference.** A graph
compiles to a `.py` the component points at, so the scene never knows graphs
exist. That is a feature: scenes stay portable, and graphs stay reusable
across scenes, exactly as `.py` scripts already are. But it also means a
missing generated `.py` fails at script-load time, not graph-load time — the
editor should surface that as a clear "graph has not been compiled" message
rather than a file-not-found in the log.

## Verification standard

Inherited from the existing plan work, and the same bar:

- Headless Python suites, no GL context, no window.
- Explicit `PYTHONPATH` to the Release output.
- Real assertions on read-back values, never "did not throw".
- MSBuild Release **and** Debug.
- Never call `Scene::OnRuntimeStop()` or drive `ScriptEngine::OnUpdateEntity`
  standalone — both are known to segfault for pre-existing reasons.
- For the editor panel: screenshots of the actual rendered graph, not a clean
  build log.
